Product

An agent orchestration OS
built for software delivery

Cosmos is an AI engineering-expert orchestration and governance platform for software teams: create reusable “Experts”, trigger them manually or from GitHub and Slack events, let them complete code tasks in isolated environments, and require human approval at every critical risk point.

Positioning

What Cosmos is

Its primary objects are tasks, runs, events, artifacts, and approvals — not just messages. It starts from one observation: individual engineers already use agents to write code, but that leverage is stuck in personal terminals — the organization can neither reuse nor govern it.

Cosmos lifts that capability to the organizational level: squads of Experts run on reproducible Environments, kept on watch by Automations across the full delivery lifecycle, sharing memory through Files — safe by default, configured through conversation, humans at judgment points, work happening where it already lives.

What Cosmos is not

An IDE plugin that only does code completion
A one-shot Q&A chatbot
A fully automatic production-release tool with no approvals or audit
A general low-code workflow platform — v1 serves software engineering only

Who it's for: engineering organizations of 20–500 people with mature GitHub + Slack usage, internal conventions, and repetitive tasks; and the EMs, tech leads, and everyday developers weighed down by PR backlogs and scarce review capacity.

Expert — a reusable workflow product surface

An Expert packages everything that makes an engineering workflow feel like a product instead of a one-off prompt. Its configuration page reads like configuring a service, not a prompt playground:

Field groupContents
Identity & sharingName, description, visibility (private / shared), stable ID; published revisions are immutable and fully traceable
InstructionsSystem prompt, user-facing instructions, and launch guidance for the person starting a session
ModelA default model chosen from the governed catalog, swappable per need
CapabilitiesTools, MCP servers, Skills, integrations — countable capability chips, not a vague “integrations” sentence
EnvironmentThe bound cloud sandbox or self-hosted daemon pool
WorkersAn explicit list of other Experts it may delegate to
TriggersPersistent event bindings — disarmed by default when created

Environment — compute and consistency

Experts access the filesystem, repositories, and tool execution inside an Environment. Environments are decoupled from Experts: one environment can serve many Experts, and one Expert can switch environments.

TypeTraitsUse when
Cloud sandboxEach session boots from a snapshot; reproducible, isolated, concurrentThe team's default path
Self-hosted daemonRuns on your laptop, VPC, or dedicated hardware; disks can persistPrivate networks, regulated data, special hardware

An environment packages the base image, repository bindings, environment variables, secret references, hooks, and network policy; active revisions are immutable and provisioning has a full timeline.

Session — where humans meet the work

A session is the meeting point of an Expert (behavior) and an Environment (machine): you set the goal, watch the turns, follow the tool calls. Conversations are kept forever; idle environments pause automatically and resume when you send the next message. Trigger-started sessions can auto-archive and remain openable.

  • Timeline: plans, steps, tool-call summaries, logs, file diffs, and check results per turn — raw logs collapsed by default, conclusions and anomalies surfaced.
  • The right rail is a product surface, not decoration: Artifacts (PRs, branches, links — durable outputs), Workers (the delegation tree), Files (workspace and org/user memory), plus live status and environment info.
  • Visibility & sharing: sessions from shared Experts or automations default to shared; personal-Expert sessions default to private; share person-by-person with a copyable link.

Automation — standing orders from events to Experts

At the product level, an “automation” equals “an Expert plus its triggers.” Three distinct paths bring events into the system:

ConceptCreated byLifecycleOn match
TriggerA human, in the Expert's configPersistentOpens a new session; the event payload becomes the first message
SubscriptionThe agent, at runtimeDies with the sessionDelivers the event into the existing session
AutomationProduct-level view= Expert + its triggersManaged, enabled, and paused as a standing order

Trigger sources cover github, gitlab, linear, slack, pagerduty, schedule (five-field cron + timezone, singleton runs: a still-running previous run skips the next), and webhook (JSONLogic filters evaluated before any session opens). The events log records every inbound fact; run history records what Experts actually did — two different questions, answered separately. Each trigger can cap runs per minute.

Files — organizational memory across sessions

Files outlive VMs. They are not an upload box — Experts write them as a side effect of work, synced at turn boundaries. Every write produces an immutable version with attribution; deletion is a tombstone, not an erasure.

ScopeVisible toTypical path
UserOnly your own sessionsuser/notes/…
OrganizationThe whole organizationorganization/pr-reviews/…
WorkspaceOnly the current session's live VM/workspace

Skills are a special directory in the file system: write your team's methodology as skill files, bind them to an Expert, and they are folded into its system prompt automatically.

Workers — why not one super-agent

Focused intent produces focused quality. Deep review and code authoring optimize for different things; one giant prompt does neither well. Cosmos offers three delegation modes:

ModeWhat it isWeightUse when
WorkerAn independent session of another Expert — openable and auditableHeavyThe subtask needs its own environment or produces side effects
SubagentA lightweight helper inside the same sessionLightResearch and verification within the same repo
Expert-to-ExpertTwo Experts collaborating through an integration (e.g. PR comments)LooseYou want humans to see — and join — the collaboration inside the integration

Principles: prefer a single Expert; when delegation is needed, use one or two clearly bounded Workers — and configuration is always explicit, never implicit fan-out.

Space — the multi-team boundary

Spaces group Experts, Environments, Sessions, Secrets, MCP, Webhooks, and repositories per team. Switching Space switches the entire context: focused lists, isolated credentials, the team's own default Expert and Environment. Every organization has an undeletable Default Space that owns unassigned resources.

Interaction Philosophy

Four interaction principles

Not slogans — concrete design decisions visible on every screen.

Advisor-first

Configuration by conversation

Successful users configure through the Advisor instead of clicking through forms: connect dependencies → build the environment → deploy or design an Expert → analyze and tune from session data. The Advisor follows a controlled plan → diff → confirm → execute chain and only performs low-risk control-plane writes; OAuth and secret operations always keep a human step.

Safe by default

Disarmed until enabled

New automations deploy off: dry-run first, then enable. Pausing keeps configuration; event filters run before any session opens, so irrelevant events cost nothing. Compliance teams define auto-approvable paths and audit trails before automation widens.

Human at judgment

Humans at judgment points

The Deep Reviewer is non-interactive — read its conclusions. The Pair Reviewer is interactive — a human makes the final call. The Risk Analyzer routes, pulling people in only on high risk. Human time goes to architecture, product, security, and release judgment.

Meet the work

Work where it lives

Enter from the web, a mobile browser, Slack, or a GitHub event; progress, approvals, and results flow back to the original thread. Nobody is forced back into an IDE sidebar, and no new information silo is created.

Information Architecture

Navigation as worldview

“Doing work” (Home / Sessions) is separated from “installing the system” (Configuration) because daily users and platform admins think differently. Automations are separate from Sessions because standing orders and conversation records are different things. The events log is separate from run history because inbound facts and actual responses answer different questions.

Files stand as their own group — they are a memory layer, not attachments. Triggers hang off Experts — the Automations page is “Experts with triggers,” not a third entity editor.

Under the Hood

A contract-driven, separated architecture

A shared contracts package constrains API, Worker, and Web alike — three surfaces, one set of generated types. Control-plane writes carry idempotency keys, optimistic concurrency, append-only audit, and an outbox.

Frontend

React + Vite

18 production surfaces across sessions, approvals, automations, and every configuration catalog; bilingual (中文/English); desktop and 390px small screens are both first-class; loading, empty, error, and permission states complete.

Backend

Fastify + PostgreSQL

An authoritative session state machine, SSE live event streams, versioned SQL migrations; FORCE RLS on every tenant table; no-login runtime roles without table ownership — misconfiguration refuses to boot.

Execution

Worker runtime

Independent worker processes execute session turns and write periodic heartbeats; the API only advertises execution capability while a fresh heartbeat exists — offline means a readable control plane, never fake success.

Contracts

Shared contracts + OpenAPI

Zod DTOs and runtime validation shared across the stack; the OpenAPI contract evolves with the code, guarded by route-coverage tests — documentation and implementation are not allowed to drift.

Storage

Object storage & quotas

S3-compatible storage backs files and artifacts with SHA-256 integrity checks, retention and orphan GC, and per-organization storage quotas.

Operations

Observability & drills

Low-cardinality metrics, SLO alert rules, backup/recovery with PITR preflight, and load / dependency-failure drill scripts — production discipline ships as runbooks in the repository.
