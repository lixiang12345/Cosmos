Getting Started

Quickstart#

Bring up the full local runtime — PostgreSQL, API, Worker, and the Web console — in five minutes.

Requirements

  • Node.js 22 and pnpm 11.7
  • Docker (with Docker Compose)
  • Optional: credentials for an OpenAI-compatible model provider (for real execution)

Install and run

terminal
pnpm install
pnpm dev

pnpm dev starts the Docker Compose runtime. Compose waits for PostgreSQL to become healthy before starting the API; the API finishes database migrations before Worker and Web start; Web reverse-proxies same-origin /api/* to the API.

Entry pointAddress
Web consolehttp://127.0.0.1:5173
API health checkhttp://127.0.0.1:8787/api/health

Configure provider credentials

On first use, copy .env.example to .env.local and fill in provider settings. Sensitive configuration is injected into the Worker only — it never reaches the browser bundle.

The console runs without credentials. The Worker stays failed and is flagged unavailable by its health check; execution can't start, but the entire control plane (Experts, Environments, Automations, catalogs) remains usable. That is deliberate safe failure, not a bug.

Frontend demo only

terminal
# Seeded frontend prototype — not the real runtime
pnpm dev:demo

Demo mode only allows a loopback local identity; production bundles always refuse to enter demo mode.

If the default ports are taken

terminal
PORT=8790 VITE_API_PROXY_TARGET=http://127.0.0.1:8790 pnpm dev

Concepts

Core concepts#

Cosmos keeps its naming consistent — Experts and Sessions are always called exactly that, never “bots” or “assistants.”

TermDefinition
ExpertA reusable agent definition: responsibilities, instructions, model, capabilities, environment, and policy — published revisions are immutable
SessionA goal-driven, long-running execution instance, created by a person or an event; conversations are kept forever
RunOne execution attempt within a session; a retry produces a new run
TriggerA manual or external-event condition that starts an Expert; attached to the Expert, disarmed when created
EnvironmentThe isolated runtime where code and tools execute: a cloud sandbox or a self-hosted daemon
ApprovalA recorded human decision on a high-risk write, showing risk, impact, evidence, and expiry
ArtifactDeliverable outputs — diffs, commits, PRs, reports, test results — searchable across sessions
SpaceThe team boundary: Experts, Environments, Sessions, and credentials are isolated per Space

For the full conceptual model, see Product · Seven first-class citizens.

Workflow

Creating Experts#

An Expert is the product surface of a team workflow. Start from a built-in template (PR Author, Deep Reviewer, Pair Reviewer, Verifier, Ticket Dispatcher, Incident Investigator) and append your repo scope and local conventions.

  1. Create a draft

    Go to Configuration → Experts and click “Create expert.” Start blank, or pick a template to pre-fill instructions and boundary conventions.

  2. State the responsibility and instructions

    Name and description say what the Expert does — and doesn't do. The system prompt carries workflow steps and acceptance rules; user instructions and launch guidance tell the person starting a session how to describe the task.

  3. Bind an environment and a model

    Pick the runtime environment and default model in the System section. Models come from the governed catalog (claude-fable-5, claude-opus-4-8, claude-sonnet-5, gpt-5.6-sol, grok-4.5); anything outside the catalog fails closed before any network request.

  4. Add capabilities and delegation

    Add tools, MCP servers, and Skills as chips; list delegable Experts explicitly under Workers. Fewer capabilities is better — least privilege is the default posture.

  5. Set visibility and publish

    Private Experts serve only you; shared Experts serve the whole Space. “Save draft” stays editable; “Publish” creates an immutable revision — production always runs a specific, known version. The danger zone offers disable and archive; archiving never deletes history.

Publishing ≠ auto-running. An Expert's triggers remain disarmed after publish. Enable them explicitly under Automations before they respond to events.

Configuring Environments#

Under Configuration → Environments, click “Create environment” and choose the type first:

TypeDescriptionChoose when
Cloud sandboxEach session boots from a snapshot; reproducible, isolated, concurrentThe team default
Daemon poolSelf-hosted processes register as execution nodes with capability tags and concurrency slots; liveness by heartbeatPrivate networks, regulated data, dedicated hardware

Environment configuration covers the base image, repository bindings (which codebases Experts may check out — also the authorization boundary for Context Engine retrieval), environment variables, secret references (picked from the Space's active Secrets), hooks, and network policy.

Environment revisions are likewise immutable once active. Failed provisioning can be retried; disabling never touches the records of past sessions. Daemon nodes are managed under Configuration → Daemons and can be toggled individually.

Running Sessions#

Start from Home

Pick an Expert and the composer placeholder adapts to its launch guidance. Describe the goal, not the steps — steps are the Expert's job. In real deployments you can pre-check codebase evidence via Context Engine and attach it to the first message as explicitly untrusted repository evidence.

Reading the timeline

The timeline shows plans, steps, tool-call summaries, logs, file diffs, and check results per turn — raw logs collapsed, conclusions and anomalies surfaced. Updates stream live over SSE; no refreshing.

Three things in the right rail

  • Artifacts: durable outputs — PRs, branches, links; add links manually too. The global Artifacts page searches across sessions.
  • Workers: the delegation tree of this session; every worker is a real, openable session.
  • Files: a preview of the current workspace and org/user memory.

Lifecycle controls

Sessions pause, resume, and cancel; a failed turn can be retried (creating a new run). Lists support pinning and archiving; archives are restorable. Conversations are kept forever; idle environments pause automatically and resume on your next message. The share panel grants per-person view access with a copyable link.

No “start execution” button? The deployment has no live Worker (or execution is switched off). The control plane still works — save a draft; once a Worker heartbeat returns, you can start. The system never renders an unexecuted session as a success.

Automations & triggers#

The Automations page is “Experts with their triggers”: one row per Expert; expand it to see its triggers and enable switches.

Seven trigger sources

SourceTypical use
github / gitlabStart a reviewer when a PR opens; start a fixer when CI fails
slackAn @mention opens a task session; results post back to the thread
linear / pagerdutyTicket transitions; alerts trigger root-cause analysis
scheduleFive-field cron + timezone; singleton runs — if the previous run is still going, this one is skipped, never queued or backfilled
webhookThe escape hatch; JSONLogic filters run before any session opens, so unmatched events cost nothing

Safe defaults

  • New triggers ship disarmed. Deploy → dry-run once → confirm the behavior → enable.
  • Pause without delete. Disabling flips a switch; configuration and history stay intact. Removing a trigger never harms the Expert.
  • Rate limits as a backstop. Each trigger can cap runs per minute, so an event storm can't stampede your environments.
  • Fire-and-forget, optionally. Trigger-started sessions can auto-archive — and archived sessions remain fully auditable.

Two ledgers

The Events log records every inbound event with a redacted payload — “what happened out there.” Run history records the runs Experts actually started — “what we did about it.” When debugging “why didn't it fire,” always read the former before the latter.

Handling approvals#

When an Expert is about to take a high-risk action (an external write, a dangerous tool call), the run stops at an approval gate. The approval card shows the action, its impact, the supporting evidence, and an expiry.

DecisionEffect
ApproveThe action executes; the decision and the decision-maker enter the audit stream
Request changesFeedback returns to the Expert, which adjusts and asks again
RejectThe action does not execute; the session continues or wraps up per the Expert's policy

Two places to act: the unified inbox on the Approvals page (cross-session, ideal for on-call), or inline in the session timeline (fullest context). Expired approvals become void — an Expert never executes on stale authorization.

Files & Skills#

The Files page shows two trees: Organization (shared org-wide) and User (visible only to your sessions). They are not an upload box — Experts write review conclusions, convention digests, and investigation notes as a side effect of work, readable by the next session, another Expert, or a teammate.

  • Every write creates an immutable version with attribution (which Expert, which session); deletion is a tombstone, not an erasure.
  • A third scope exists inside sessions: /workspace — the live VM disk, visible only within that session.
  • Storage is S3-compatible with SHA-256 integrity checks and per-organization quotas.

Skills: methodology as files

Maintain skill entries under Configuration → Skills (say, “our migration safety checklist”). Bind a skill to an Expert and its content is folded into that Expert's system prompt, ordered by name — best practices go from word of mouth to organizational default.

Configuration

Integrations & credentials#

Integrations

Eight types: github, gitlab, slack, jira, pagerduty, linear, datadog, and custom. Connect once; any Expert can listen. Cards show connection status and health; action_required offers a repair path, and disconnect and archive are distinct operations.

MCP servers

Three transports: stdio (launch command), and sse / http (endpoint URL). Partner presets for Atlassian, Sentry, Stripe, and Figma pre-fill in one click. Registered servers appear as capability chips in the Expert editor.

Webhooks

Creating a webhook yields a dedicated delivery URL (POST …/webhooks/{id} with Bearer auth) and a signing secret (whsec_…) that is shown exactly once — store it immediately; every later view shows only the last four characters. The UI provides a copyable curl test command. HTTPS targets only.

Secrets

Names must match ^[A-Z][A-Z0-9_]*$ (e.g. DEPLOY_TOKEN). Ciphertext is write-only: the database grants no read on the ciphertext column, so any query returns a last-four mask at most. Environments consume secrets by reference; rotation means swapping the reference.

Repositories

Register GitHub / GitLab repositories and default branches — the basis for environment repo bindings and the authorization boundary for Context Engine retrieval. Connection problems are surfaced explicitly as action_required.

Credential discipline: provider API keys are injected into the Worker from a secret manager. No plaintext key should ever appear in the browser bundle, URLs, localStorage, logs, or screenshots.

Operations

Deployment & operations#

Build production images

terminal
docker build -f apps/api/Dockerfile -t cosmos-api .
docker build -f apps/web/Dockerfile -t cosmos-web \
  --build-arg VITE_OIDC_AUTHORITY=https://identity.example.com/ \
  --build-arg VITE_OIDC_CLIENT_ID=cosmos-web \
  --build-arg VITE_OIDC_AUDIENCE=cosmos-api \
  --build-arg VITE_OIDC_REDIRECT_URI=https://cosmos.example.com/auth/callback \
  --build-arg VITE_OIDC_POST_LOGOUT_REDIRECT_URI=https://cosmos.example.com/ \
  --build-arg VITE_OIDC_SILENT_REDIRECT_URI=https://cosmos.example.com/auth/silent-callback .

Both runtime images run as non-root with built-in health checks. The Web container reverse-proxies same-origin /api/* to COSMOS_API_UPSTREAM and requires explicit HTTPS origins for IdP/API via COSMOS_CSP_CONNECT_SRC and friends.

Migrations are a separate job

Startup migrations are forbidden in staging/production. Releases first run node dist/migrate.js as a standalone job from the same image, then roll the API. The migration identity owns schema work and runtime-role hardening; API/Worker login identities only receive role membership — no table ownership. Mismatched roles refuse to boot (fail closed).

Required production configuration

ComponentKey variables
APINODE_ENV=production · AUTH_MODE=oidc · DATABASE_URL · CORS_ORIGIN · OIDC_ISSUER / OIDC_AUDIENCE / OIDC_JWKS_URI · SECURITY_AUDIT_HMAC_KEY (with a stable …_KEY_ID)
WorkerA unique, stable WORKER_ID · AGENT_PROVIDER_GPT_API_KEY / AGENT_PROVIDER_CLAUDE_API_KEY / AGENT_PROVIDER_GROK_API_KEY (injected from a secret manager) · EXECUTION_ENABLED=true
WebVITE_AUTH_MODE=oidc plus the OIDC public-client settings; missing identity configuration shows an error instead of silently entering demo mode

Probes and metrics

  • GET /api/health — the only public liveness probe.
  • GET /api/ready — authenticated; validates database and migration state, rejecting both pending and unknown migration history.
  • GET /api/metrics — exposed only when METRICS_SCRAPE_TOKEN is configured; low-cardinality HTTP/SSE metrics.

Workers write periodic database heartbeats; the API advertises execution capability only while a fresh heartbeat exists. With Workers offline, the control plane stays readable and session drafts can be saved.

Quality gates and runbooks

terminal
pnpm check          # lint + typecheck + tests + build
pnpm openapi:lint   # API contract validation

The repository ships three operations runbooks: PostgreSQL backup & recovery (with PITR preflight and quarterly drills), observability & SLO alerting, and load / dependency-failure drills. CI enforces frozen-lockfile installs, integration tests, backup-restore verification, image scanning, and redacted secret scanning.

Troubleshooting#

Can't start execution / send button disabled

That is the honest rendering of execution capability being unavailable. Check in order: is the Worker container healthy (fresh heartbeat)? → are provider credentials configured in .env.local? → is EXECUTION_ENABLED=true? The control plane is unaffected — configuration work continues as normal.

A trigger didn't open a session

Read the Events log first: did the event arrive, and did a filter stop it? Then Run history: did the per-minute rate cap hit, or is the trigger still disarmed? Schedule triggers are singletons — a still-running previous run makes the next one skip, by design.

Default ports are taken

Override both the API port and the Vite proxy target: PORT=8790 VITE_API_PROXY_TARGET=http://127.0.0.1:8790 pnpm dev.

Cross-origin API requests rejected

For split, cross-origin deployments set both VITE_API_BASE_URL and a comma-separated VITE_API_ALLOWED_ORIGINS; otherwise the browser refuses to send the Bearer token — protection against credential leakage, not a bug.

Context Engine connection fails

Staging/production require HTTPS endpoints. For local Compose, reach a host-machine plugin at http://host.docker.internal:8790 and set CONTEXT_ENGINE_ALLOW_INSECURE_HTTP=true in local .env.local only. Also confirm the Space's active environment binds the target repository — the binding is the retrieval authorization boundary.

Common questions

  • Mistyped a secret and want to peek? You can't. Ciphertext is write-only — create a correct one and swap the reference.
  • Does archiving lose data? No. Archived sessions, triggers, and catalog entries keep full history, and most can be restored.
  • Why can't I add arbitrary models? The catalog is governed by shared contracts and everything outside it fails closed — in exchange you get per-family credential isolation and predictable behavior.

Still stuck? The repository's docs/ directory holds the product requirements, production architecture baseline, and three operations runbooks — deeper boundaries and recovery flows than this guide covers.
